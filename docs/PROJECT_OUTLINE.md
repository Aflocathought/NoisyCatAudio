# 项目大纲：Rust Spectral Resonator

文档日期：2026-09-26。状态：设计基线；M1 透明 STFT 收到 Bitwig 延迟反馈，M2 整数频点研究原型完成源码与 CLAP 验证，尚待新版宿主试听。

## 1. 项目目标

开发一个可以在 Bitwig Studio 中使用的频谱共鸣效果器。输入鼓、人声、噪声或其他音频，由输入的频谱能量激励一组可调音的共鸣成分，产生短促的有音高打击声或持续衰减的泛音尾音。音高先由内部音符选择器控制，再支持 MIDI 单音和复音。

声音方向参考 Ableton Live 的 Spectral Resonator。根据 Ableton 的开发者访谈，原版使用 FFT 将音频转为频谱信息，在频谱域处理，再使用 IFFT 重建声音。其完整算法未公开。本项目实现自己的频谱共鸣模型，不宣称复制其内部算法或逐样本复现其音色。

用户已明确倾向 Rust，主要考虑自己维护代码时的内存安全。项目因此以 Rust DSP 和 Rust 插件框架为主，减少自行编写的底层不安全接口。

## 2. 成功时应当能够做到什么

在 Bitwig 的音频轨道中加载插件，播放鼓循环，选择一个内部音符，可以听到与该音高相关、具有自然衰减的共鸣。将另一条轨道的音符通过 Note Receiver 等宿主路由送入插件后，共鸣音高可以随音符变化。停止输入时，已有尾音继续衰减；关闭编辑器不影响音频处理。立体声输入的左右信息必须保留，共鸣与尾音也分别在左右声道处理。

后续界面应能清楚显示输入、输出和当前共鸣结构。频谱滚动平滑，但界面帧率不被用来代表 DSP 分析延迟或频率分辨率。

## 3. 已确定的技术选择

| 决策 | 当前选择 | 原因与边界 |
| --- | --- | --- |
| 实现语言 | Rust | 自有 DSP 核心禁止 `unsafe`；底层依赖仍需要版本和接口审查 |
| 第一目标平台 | Windows x86-64 | 当前开发环境和首个宿主验证平台 |
| 第一插件格式 | CLAP | Bitwig 支持良好，框架已有音符和参数调制能力 |
| 后续插件格式 | VST3 | DSP 共用，但需要独立验证打包、事件和状态恢复 |
| 插件框架 | nice-plug，锁定可验证版本 | 来自 NIH-plug 的社区分支；上游当前仍标为实验性 |
| FFT | RustFFT，必要时使用 RealFFT 实数包装 | 复用成熟 CPU FFT 实现；计划和 scratch 在初始化阶段建立 |
| 分析方法 | 固定分辨率 STFT 起步 | 先建立透明重建和可测量基线，再评估多分辨率方案 |
| 目标声音引擎 | 频谱分析、逐泛音状态、IFFT 重建 | 精确频率合成需要单独验证；不能用最近 FFT 频点代替最终音准 |
| 普通界面 | egui | 复用参数、交互和布局能力 |
| 密集可视化 | wgpu，按阶段引入 | 绘制频谱纹理和动态曲线；不将实时音频计算搬到 GPU |

本机已核实 Rust/Cargo 1.92.0。查阅的 nice-plug 主分支声明 Rust 1.88 和 Edition 2024；这只能说明框架声明的最低版本，不证明所有 GUI 传递依赖已经在本机通过编译。第一次建立工程时必须生成并提交 Cargo.lock，记录实际依赖和工具链。

## 4. 先复用什么

优先参考 nice-plug 的 gain、STFT、MIDI、复音调制和 egui/wgpu 示例，复用参数系统、宿主适配和窗口嵌入。STFT 示例展示的是 FFT 卷积与 overlap-add 接口，不能直接当作完整的频谱共鸣器。

复用 RustFFT/RealFFT 的规划器和执行接口，不自行实现 FFT。界面复用 egui 与宿主嵌入适配器，不自行设计窗口系统。CPU 与界面之间优先使用经过审查的预分配 SPSC 队列，不自行实现无锁内存回收。

Vital 的公开 OpenGL 渲染代码可作为架构参考；其代码许可证与本项目采用的框架不同，不直接将参考源码复制成自己的实现。MiniMeters 可以作为显示体验参考，Serum 2 的内部技术栈不作为本项目的已确认依据。

## 5. 首个可演奏版本的范围

首个可演奏版本是 M3 完成后的版本，不等同于 M0 的“能加载”，也不等同于 M2 的“能响”。

| 能力 | 首个可演奏版本 |
| --- | --- |
| 输入与输出 | 支持 1→1 和 2→2；立体声是首个可演奏版本的必备能力，左右声道保留独立分析与共鸣状态 |
| 调音来源 | 内部音符选择、MIDI 单音 |
| 音高 | 十二平均律音符，目标频率不吸附到 FFT 整数频点 |
| 基音范围 | 暂定 MIDI 33–93，即约 55–1760 Hz；作为验证范围而非已完成性能 |
| 泛音 | 暂定最多 64 个，自动排除接近或超过 Nyquist 的分量 |
| 衰减 | 使用 T60 定义，暂定 0.05–12 秒 |
| 音色控制 | 激励增益、整体衰减、高低频衰减修正 |
| 混合 | 低／中／高三频段 crossover：低、高保留干声，中频输出湿声；调整两个分频点与输出增益 |
| 保存恢复 | 参数与状态版本号；不保存运行中的频谱尾音 |
| 可视化 | 基础电平和输入/输出频谱；复杂动画不是 M3 的前置条件 |

以下功能不进入首个可演奏版本：MIDI 复音、MPE、连续滑音、Stretch、输入移调、Unison、Granular、冻结、多分辨率/CQT、可任意绘制的音阶和商用安装器。冻结是可能的独立扩展，不当作原版 Spectral Resonator 的必备功能。

## 6. 功能如何逐步扩展

M3 后优先增加 4–8 声部复音，解决音符识别、尾音、声部抢占与电平累加。之后再增加 Unison、逐泛音 Wander、Stretch 等音色能力。连续音高调制需要重新验证相位、核函数更新和瞬态，不能只把整数音符参数改成浮点数。首版 crossover 采用固定频段路由，不提供全局或逐段 Mix；若以后开放每段比例，应重新定义参数、状态迁移和重组验收。

普通泛音列满足 `f_h = h × f0`，不保证每个泛音都是十二平均律中的调内音。若以后增加音阶量化，需要明确它改变的是目标共鸣频率，并处理量化后多个泛音落在同一频率时的增益。

CQT 或多分辨率 STFT 的引入由听感与测量驱动：只有当低频稳定性与高频瞬态无法在单窗口中取得合适平衡时再评估。它们不会免费消除低频精细分析所需的观察时间。

## 7. 开发里程碑与退出条件

| 阶段 | 工作内容 | 必须通过的验收 | 本阶段不能宣称什么 |
| --- | --- | --- | --- |
| M0 宿主接入 | workspace、CLAP 增益插件、稳定参数 ID、打包 | Bitwig 扫描与加载；左右声道独立传递；保存/重开工程；多实例；无编辑器也能工作 | 不能宣称已经有共鸣算法 |
| M1 透明 STFT | 分析窗、FFT/IFFT、重叠相加、缓冲与延迟 | 单声道和立体声对齐后透明重建；左右无串音；变量块大小；采样率切换；延迟报告匹配脉冲测试 | 不能以画出频谱作为音频正确性的证据 |
| M2 共鸣研究原型 | 整数频点复数状态、衰减、激励归一化 | 无输入时稳定衰减；相位连续；T60 可测；输出无非有限值 | 不能把频点吸附的音高当成音乐级音准 |
| M3 精确单音 | 分数频率分析参考、精确频率合成、MIDI 单音、阻尼与三频段 crossover | 目标频率误差、衰减、分频重组与左右独立性、离线参考对照、Bitwig 实际演奏检查 | 不能宣称与 Live 音色等价或具有未实现的复音 |
| M4 复音与音色 | 4–8 声部、抢占、尾音、电平管理；逐项添加调制 | 密集音符、重叠音符、持续踏板、Panic、CPU 高分位耗时 | 不能把平均 CPU 低当成不会爆音 |
| M5 GPU 编辑器 | egui 参数编辑、wgpu 频谱纹理、DPI/缩放、暂停绘制 | 编辑器反复开关、多实例、显卡后端、稳定帧时间；音频不受阻塞 | 不能把 60 FPS 等同于 16.7 ms 音频延迟 |
| M6 发布准备 | VST3、状态迁移、依赖审查、发布构建与说明 | 两种格式分别验证；干净环境加载；可重建版本与许可证清单 | 不能把调试构建当成正式发行物 |

阶段按验收顺序推进，不预先承诺固定开发天数。M3 的精确频率合成与音色校准是当前最大的算法不确定性，M0/M5 的窗口生命周期与依赖组合是主要宿主集成不确定性。

## 8. 质量原则

自有 DSP crate 使用 `#![forbid(unsafe_code)]`。这条规则限制本项目代码，不能被解释为整个依赖树没有 `unsafe`。音频回调中不分配堆内存，不获取阻塞锁，不读写文件，不等待 GPU，也不释放最后一个持有大型资源的引用计数对象。

UI 数据允许在消费者跟不上时降采样或丢弃过期显示数据，音频与音符处理不能采用同样的丢弃策略。任何优化都必须保留透明重建、音准、衰减和事件时序测试。

文档、源码单元测试、离线参考输出、宿主测试和实际听感分别记录。每条完成声明必须能指向对应证据。
